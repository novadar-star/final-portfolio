You are rebuilding my personal portfolio.

Your job is NOT to make it look more polished.

Your job is to make it feel more authored, specific, human, and unmistakably mine.

The current site is clean, but it feels AI-generated because it follows too many predictable portfolio conventions: polished capability sections, status/currently blocks, tech-logo walls, tidy personal-brand copy, generic card systems, repetitive section framing, and language that sounds strategically written instead of naturally authored.

I want you to actively REMOVE that feeling.

## 1. FIRST: INSPECT THE EXISTING REPO

Before changing anything, inspect the current implementation and understand:

* framework
* routing
* component structure
* styling system
* typography
* assets
* project content/data structure
* dependencies
* responsive behavior
* deployment setup
* what parts of the current version are reusable

Do not immediately rewrite from scratch.

Do not introduce a new framework, CMS, database, state-management library, animation framework, or major dependency unless absolutely necessary.

Preserve anything technically sound.

The redesign should be a focused product/design rewrite, not an infrastructure rewrite.

# CORE GOAL

The portfolio should feel like:

> a curious technical person’s personal corner of the internet

NOT:

> a professionally optimized AI automation developer portfolio

The site should make someone think:

> “this person is interesting. wait, she built that?”

instead of:

> “this person has AI, automation, cloud, product, and marketing skills.”

The difference matters.

Do not explicitly try to “communicate my personal brand” in every section.

Let the personality emerge through:

* project selection
* writing
* visual composition
* small details
* artifacts
* unexpected transitions
* imperfect/asymmetric layouts
* the way information is grouped

Do not explain my personality to the visitor.

Show it.

My work sits somewhere around:

The portfolio must still look complete if I do not update it for 6 months.

# HOMEPAGE STRUCTURE

Do not create a conventional:

Hero → About → Skills → Projects → Experience → Contact

portfolio.

Use this loose structure instead.

## 1. OPENING

The opening should be extremely simple.

My name/identity should be obvious.

“nova.” can remain part of the branding, but my real name should also be available somewhere naturally so recruiters do not have to decode who I am.

The hero does NOT need a giant title describing my profession.

Do not write:

> AI Automation Developer & Cloud Builder

Do not write:

> Building intelligent systems at the intersection of AI and automation.

Instead, write something that sounds like an actual human introduction.

Possible tone:

> hey, i’m nova.

> i make things, automate things, break things, then usually figure out why.

This is only directional. Improve it if you can make it sound more natural and less “written.”

Keep the hero visually sparse.

No giant CTA buttons.

No “View My Work / Contact Me” SaaS-style button pair.

A subtle path into the projects is enough.

---

# 2. PROJECTS SHOULD DOMINATE THE SITE

The homepage should teach people who I am THROUGH what I have made.

Do not create identical project cards.

Each project may be composed differently depending on its content.

One could be:

large screenshot + handwritten-style annotation + text

Another could be:

workflow diagram + short description

Another could be:

two stacked screenshots + result

Another could feel almost like a notebook entry.

The projects should feel like ARTIFACTS, not portfolio cards.

For each important project, communicate some version of:

* what made me build it
* what the thing actually does
* one interesting technical/product decision
* what happened / what I learned

Do not force these into visible headings called:

Problem
Solution
Impact
Stack

That structure is useful internally but too portfolio-like visually.

Write it like a person explaining the thing.

Example tone:

> applying to jobs was repetitive, so i built a workflow that finds listings, scores them against my resume, and generates a version worth actually reviewing.

That is stronger than:

> Problem: Job seekers spend significant time reviewing irrelevant roles.

Do this across the site.

---

# 3. PROJECT HIERARCHY

Use approximately:

* 2–4 flagship projects
* several smaller things/experiments

Flagship projects get visual depth.

Smaller projects should NOT become another polished grid.

Consider a loose list, index, archive, annotation wall, or compact artifact collection.

Examples of potentially relevant work include:

* job scraper / resume workflow
* GTM signal-to-outreach automation
* AI intern assistant
* AI/product experiments
* AWS/cloud work
* hackathon projects
* marketing automation
* community-related systems

Do not invent outcomes or metrics.

Use only information that exists in the current repo/content.

If information is missing, leave it understated rather than hallucinating.

---

# 4. EXPERIENCE / LEADERSHIP

Do not build a standard vertical resume timeline unless the content genuinely benefits from it.

Experience should feel compact and credible.

I want people to understand that I have:

* participated in projects/hackathons

without recreating my resume on the page.

# 6. TECH STACK

The tech stack should be SECONDARY.

I want visual authorship, not visual spectacle.

Think:

* personal publication
* notebook
* scrapbook
* technical lab notes

* editorial page
* messy-but-intentional desk

No cheesy taped-paper effect on every block.

Borrow the PRINCIPLE:

Allow:

* small annotations
* project-specific layouts
* marginal text
* unexpected typography scale changes
* whitespace
* images that break the grid

Controlled irregularity.

Not chaos.

# TYPOGRAPHY

Typography should carry much of the personality.

Avoid the predictable:

Inter everywhere
large bold sans-serif
monospace tags
tiny uppercase eyebrow labels

combination.

Use at most 2 primary typefaces unless the existing system justifies another.

Consider combining:

* a neutral/readable sans
  with
* a serif, humanist, or distinctive editorial face

OR another combination that feels authored.

Do not choose fonts merely because they are popular in developer portfolios.

Maintain readability and performance.

---

# COLOR

Do not make this another black developer portfolio.

Do not make it another beige editorial portfolio either.

Use a restrained palette that feels personal.

Prefer:

* an off-white or slightly tinted base
* strong readable text
* one or two imperfect/accent colors

Avoid:

* cyber blue
* purple AI gradients
* neon green hacker aesthetic

Color should appear as punctuation, not decoration.

---

# INTERACTIONS

The site needs very few interactions.

Each interaction must have a reason.

Good examples:

* a project diagram revealing additional system details
* image inspection
* lightweight annotations appearing on hover/focus
* navigation that helps someone understand where they are

Bad examples:

* animation because “modern websites animate”
* floating cards
* scroll-jacking
* endless parallax
* mouse-follow effects
* text scrambling
* typing animations
* magnetic buttons

Prefer one memorable interaction over fifteen generic ones.

Remove or avoid anything that becomes visibly stale.

* currently building
* latest experiment

* current obsession
* status

Mobile is not a shrunk desktop.

Review every composition specifically on mobile.

Preserve personality without:

* horizontal overflow
* tiny annotations
* unreadable diagrams
* awkward project image stacking
* excessive vertical dead space

Where a desktop layout is irregular, create a deliberate mobile counterpart rather than forcing the same geometry.

# ACCESSIBILITY

Maintain:

* proper semantic HTML
* heading hierarchy
* keyboard navigation
* visible focus states
* alt text
* appropriate color contrast
* reduced motion support
* touch-friendly targets

Distinctive does not mean inaccessible.

---

# PERFORMANCE

Do not sacrifice speed for aesthetics.

Optimize images.

Avoid unnecessary JavaScript.

Prefer CSS/layout solutions where possible.

Use static rendering where appropriate.

Do not add heavyweight animation or UI libraries for minor effects.

---

# IMPORTANT: DO NOT OVER-SYSTEMATIZE THE DESIGN

This is one of the biggest requirements.

Do not create:

* ProjectCard
* ProjectCardVariant
* SkillCard
* ExperienceCard
* AboutCard
* CTASection

for every piece of content simply because componentization is possible.

Reusable primitives are good.

Visual sameness is not.

Build reusable structural primitives while allowing pages and projects to have their own composition.

Do not force every project into the same rectangle.

# IMPLEMENTATION APPROACH

Work in this order:

## Phase 1 — Audit

Inspect the current site/repo.

Identify:

* what currently feels generic
* what is worth preserving
* which sections should be deleted
* which content is actually strong
* current technical constraints

Then create a short internal implementation plan.

Do not ask me to approve every step.

Proceed.

## Phase 2 — Content cleanup

Remove:

* repetitive positioning
* capability fluff
* stale/current status UI
* unnecessary tool walls
* generic portfolio copy
* generic section labels

Do not delete factual information that can be reused elsewhere.

Reposition it.

## Phase 3 — Foundation

Establish:

* typography
* spacing
* color
* layout primitives
* content model
* image treatment
* navigation

## Phase 4 — Homepage

Build the homepage around:

identity → work/artifacts → experience/context → human layer → contact

Projects should carry most of the narrative.

## Phase 5 — Project detail experience

Flagship projects should be readable as stories.

Not formal consultant case studies.

Use screenshots, diagrams, notes, architecture, and outcomes where available.

## Phase 6 — Responsive/accessibility/performance

Test deliberately.

## Phase 7 — Final anti-AI audit

Before finishing, inspect the site as if you were trying to identify whether it was generated by an AI website builder.

Look for:

* predictable section ordering
* repetitive cards
* generic copy
* identical spacing everywhere
* excessive pill tags
* unnecessary labels
* too-perfect symmetry
* stock “creative developer” interactions
* inflated language
* design-trend mimicry
* every section having the same visual rhythm

If you find these, remove them.

# FINAL QUALITY TEST

The finished site should satisfy all of these:

### PERSONALITY

Could this exact site plausibly belong to another AI automation student after swapping the name?

If yes, redesign it.

### CONTENT

Do I learn who Nova is primarily through her work and choices rather than descriptive claims?

If no, rewrite it.

### AUTHENTICITY

Does any sentence sound like LinkedIn, a startup landing page, a career coach, or ChatGPT?

If yes, simplify it.

### VISUAL AUTHORSHIP

Does the site look like a design system generated first and content inserted later?

If yes, loosen the system.

### MAINTAINABILITY

Can I leave it untouched for six months?

If no, remove the dependency on freshness.

### PROJECTS

Do projects feel like actual things someone made rather than portfolio case-study templates?

If no, redesign them.

### MOBILE

Does the mobile version feel intentionally designed?

If no, fix it.

### PERFORMANCE

Did distinctiveness introduce unnecessary technical weight?

If yes, simplify it.
